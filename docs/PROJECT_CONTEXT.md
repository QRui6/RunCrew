# 项目上下文

## 一句话解释

RunCrew 是一个使用你自己的长期跑步数据，帮助完成“训练回顾—状态判断—风险提示—下一步建议”的个人跑步运营系统，同时用来实践可验证的 Agent 工程。

## 为什么做这个项目

市面上的跑步 App 已经能记录轨迹、配速和心率，也能给出通用训练计划。RunCrew 不试图重复做一个运动记录 App，而是研究一个更具体的问题：

> 当一个人长期训练、状态持续变化、数据来自多个来源时，如何让多个 Agent 在可靠数据和明确规则下协作，并让每个结论都可以回放、检查和纠正？

这个场景与你本人有关，因为：

- 你是实际跑步用户；
- 可以持续产生真实数据；
- 可以判断建议是否有用；
- 可以长期记录系统犯过的错误；
- 面试时能解释真实需求，而不是虚构电商案例。

## 最终想提供的用户能力

未来用户可以询问：

- 我上周训练完成得怎么样？
- 最近训练负荷是不是上升太快？
- 今天应该照常训练、降低强度还是休息？
- 为什么系统建议调整下周计划？
- 最近某个疼痛是否与训练变化同时出现？
- 某场比赛前的训练是否按计划推进？

系统回答时必须同时说明：

- 使用了哪些事实；
- 哪些数据缺失；
- 使用了什么规则或 Skill；
- 调用了什么工具；
- 结论的置信度；
- 是否需要用户确认。

## 项目不是做什么

- 不是另一个轨迹记录 App；
- 不是只靠 Prompt 生成训练计划的聊天机器人；
- 不是医疗诊断、伤病确诊或营养处方系统；
- 不是一开始就堆叠训练、伤病、营养等大量 Agent；
- 不是为了展示框架名称而创建的 Demo。

## 工程学习目标

项目后续用于实践：

- Skill：把可复用领域流程封装为明确能力；
- MCP：以标准协议读取 COROS 等外部数据；
- Context Engineering：选择、压缩和分层传递上下文；
- Harness Engineering：权限、状态、追踪、错误隔离和回放；
- Loop Engineering：让 Agent 在观察—行动—验证—修正循环中运行；
- Multi-Agent Orchestration：在确有不同职责时进行协作，而不是为多 Agent 而多 Agent；
- Evaluation：使用历史数据、故障注入和标准答案评估系统。

## 当前策略

项目采用从下到上的实施顺序：

```text
真实数据接入
→ 统一 Schema
→ 确定性分析
→ 单个 Skill
→ 单 Agent Loop
→ Harness 与评测
→ 必要的多 Agent 协作
```

当前已经完成数据竖切、FIT 详情兜底、确定性 Training Review Skill、单 Agent Context + Harness + Loop、版本化评测、DeepSeek Policy、工程观测台和跑步数据连续对话。M7 建立并评测多 Agent 训练闭环，M8-B 把它接成网页用户流程，M9-A 增加由用户确认、可追溯且能被 Planning Agent 消费的类型化长跑日偏好，M8-A2/A3 又形成了可重复演示、简历描述、核心难点、面试追问和仓库证据映射。下一步是用确定性 Weekly Training Memory 支撑跨周上下文，而不是继续机械增加角色或无依据引入向量库。
