# 核心难点与面试讲述框架

面试时不要从“我用了哪些框架”开始。每个难点用“问题—约束—方案—验证—边界”五步讲，能够自然回答为什么这样设计。

## 难点一：外部运动数据并不稳定

**问题**：COROS 的活动列表可以取得，但详情、分圈和 FIT 下载能力并不总是可用。如果把业务层直接绑定某个 MCP 返回格式，一个接口失败就会让整个活动消失。

**约束**：真实跑步数据包含隐私；FIT 解析结果必须可追溯；同步重跑不能制造重复记录。

**方案**：用 Provider 协议隔离外部厂商，将数据规范化为 `ActivitySummary / ActivityDetail`；按“详情—分圈—FIT 私有缓存—摘要”逐级降级；以 `provider + external_id` 幂等写入，同时保存原始载荷 Hash。

**验证**：真实 COROS OAuth + PKCE、MCP 工具发现和活动同步已完成；手动导出的真实 FIT 已解析出 session/lap/record；失败路径由 fixture 和自动化测试回归。

**边界**：COROS 自动 FIT URL 仍未稳定取得，不能声称全自动详情链在所有活动上可用。

## 难点二：如何既使用 LLM，又不让它编造训练事实

**问题**：把活动数据全部塞进 Prompt，让模型同时计算配速、判断负荷并写建议，输出难以复现，也无法定位错误来自数据、规则还是模型。

**约束**：个人事实必须有证据；模型输出不稳定；真实 API 有延迟和费用。

**方案**：确定性 Service/Skill 负责计算和证据，LLM 只替换 Policy 或自然语言回答；Pydantic/JSON Schema 校验 Action，Harness 管理工具白名单、参数固定、预算、重试、超时和 Trace。上下文只发送规范化活动、确定性结论和有限历史，不发送 Provider 原始载荷、坐标、Token 或 FIT。

**验证**：确定性 Policy 与真实 DeepSeek 在 `review-agent-eval/1.1` 同一 Suite Hash、15秒预算下均为12/12；真实模型报告记录了 Token、费用和延迟。

**边界**：这组真实模型评测只有一个工具和两种动作；3个非法动作场景使用脚本化 Policy 注入，只证明 Harness 防线，不证明模型自身安全。

## 难点三：多 Agent 不是多写几个角色名

**问题**：训练执行事实、恢复风险和计划推进存在真实冲突。如果一个 Agent 同时读取全部数据、做风险判断并修改计划，权限与责任无法区分。

**约束**：Recovery 不能诊断；Plan 不能跳过用户确认；节点失败不能继续执行下游错误动作。

**方案**：Execution 只对照计划与活动，Recovery 只输出保守风险和 `plan_action`，Plan 只生成草案；Coach 只消费最小 Handoff 并路由。每个节点只有一个工具权限，跨节点数据带 Hash 血缘，计划变更在 `awaiting_user_confirmation` 暂停。

**验证**：18个版本化合成场景直接运行真实 Coach Harness，覆盖正常路由、缺反馈、红旗、重试、超时、非法输出、权限、Handoff 篡改、预算和批准前状态漂移，确定性基线18/18。

**边界**：Coach 路由当前是确定性 Policy，真实 LLM 多 Agent 同题评测尚未实施。

## 难点四：用户批准前，系统状态可能已经变化

**问题**：Agent 生成减量草案后，用户可能修改偏好、切换计划或产生新反馈。直接应用旧草案会覆盖新事实。

**约束**：浏览器不应拥有提交任意计划 patch 的能力；只校验旧 `revision` 仍不足以发现所有输入变化。

**方案**：浏览器只提交 `approve/reject + comment`。批准时服务端使用原始请求重新运行 Coach，比对完整结果、planning hash 和 `revision`；变化则标记 stale，不写入。正式修改再由训练周期服务递增 revision。

**验证**：产品端到端测试和 Coach 评测都覆盖 stale 审核；长期偏好变化也会改变计划 `input_hash`，使旧草案失效。

**边界**：这是单机 SQLite 下的乐观并发与回放控制，不等同于分布式事务或高并发验证。

## 难点五：Memory 要可用，也要可审计

**问题**：直接让聊天模型把“我周日跑长距离”写进向量库，会混淆用户明确偏好、模型推断和过期事实。

**约束**：长期偏好会影响未来计划，错误写入的影响跨会话持续存在。

**方案**：长期偏好使用类型化 `preferred_long_run_weekday` 并要求显式确认；聊天只能提出带原消息引用、文本 Hash、置信边界和七天有效期的 Candidate，确认时服务端重算候选 Hash、重读原消息，再复用正式偏好服务。周训练记忆只从正式计划、已确认执行、Activity、Check-in 和已批准变更确定性生成。统一 Context Builder 再按职责、截止时间、生命周期和目标周过滤，执行字段投影与固定预算：Execution 不读记忆，Recovery 只读周聚合，Plan 读取偏好和训练基线但不接收急性症状细节。

**验证**：专项测试覆盖临时/否定/歧义候选拒绝、前端字段注入、候选和原消息篡改、确认/拒绝/替代/过期、正式偏好幂等、完整周结算、职责字段最小化、预算、双 Hash、Planning 消费和旧草案失效。

**边界**：候选提取目前只有一种类型和确定性规则，尚无真实 LLM 候选对照、向量检索或独立 Memory Eval，不应包装成完整通用记忆平台。
