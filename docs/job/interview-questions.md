# 面试追问清单

## 1. 为什么选择跑步，而不是常见电商 Agent？

因为我是长期跑步用户，能够持续获得真实数据和主观反馈。更重要的是，训练场景天然包含计划、执行、身体状态、风险和调整之间的冲突，适合验证 Agent 如何在有状态、需要人工确认的业务里协作，而不是只做一次性问答。

## 2. 为什么需要三个职责 Agent？一个 Agent 不行吗？

拆分依据不是角色名称，而是权限冲突：Execution 形成执行事实，Recovery 可能要求降级，Plan 才能生成调整草案。三者输入、工具和失败边界不同。Coach 只路由最小 Handoff；如果没有这个冲突，我会保留单 Agent。

## 3. 这是真正的 Agent，还是规则引擎套壳？

业务计算刻意由确定性 Skill 完成，Agent 价值在受约束地选择动作、组织职责节点、处理失败和暂停等待确认。单 Agent 已用真实 DeepSeek 替换 Policy 做过同题评测；多 Agent 当前先用确定性 Policy 建立 ground truth，尚未把它包装成真实 LLM 编排结果。

## 4. 为什么不用 LangGraph？

当前流程节点少，但我需要精确控制工具权限、两级超时、预算、重试、Trace、Handoff Hash 和批准前重放，所以先实现了小型显式 Harness。这样每个边界都能直接测试。若未来出现动态分支、并行节点或持久化图恢复需求，再评估迁移图框架，而不是为了关键词引入依赖。

## 5. Context Engineering 体现在哪里？

上下文分为活动事实、确定性 evidence、最近8条对话、业务状态、单次 Agent 工作状态、已确认长期偏好和版本化周训练记忆。统一 Builder 按 Execution、Recovery、Plan 做字段投影和固定预算，并记录每条候选的选中/排除原因；`context_hash` 约束实际业务输入，`audit_hash` 保留完整选择审计。Handoff 记录字段名与请求 Hash，Trace 不复制私人正文。

## 6. 如何防止模型编造用户数据？

模型不能直接计算或写入活动事实。个人事实和推断必须引用确定性 evidence；工具参数由 Harness 固定和校验；聊天回答的 evidence 类型有白名单。Provider 原始载荷、坐标和外部 ID 不进入模型上下文。

## 7. 用户点批准后为什么还要重跑一次 Agent？

因为草案生成到批准之间状态可能变化。服务端用原请求重放并比较完整结果、planning hash 和 revision；不一致就 stale。浏览器只传决定和备注，不能偷偷提交计划 patch。

## 8. Memory 为什么不用向量数据库？

当前需要记住的是少量高价值结构化偏好和周训练聚合，精确过滤职责、状态、有效期、知识截止和来源比语义相似度更重要。类型化 SQLite 更容易审计、回放和处理冲突。只有未来评测证明结构化检索不足，才考虑向量层。

## 9. 12/12 和18/18分别证明什么？

12/12证明单 Agent 在一个工具、两种动作的版本化套件中，真实 DeepSeek 与确定性 Policy 得到相同预期结果；18/18证明确定性多职责 Harness 在任务、故障、权限、血缘和审核场景下符合预期。后者不证明真实 LLM 多 Agent 稳定。

## 10. 项目中最有价值的一次失败是什么？

第一次完整 DeepSeek 评测为了避免网络超时，只给模型用例临时放宽预算，导致 Suite Hash 与确定性基线不同，结果无法公平比较。之后把15秒共享预算写进 Suite 版本，重新生成双方同 Hash 基线。这个错误让我确认评测配置本身也是产品契约。

## 11. 如何处理 COROS 详情接口失败？

不回滚已经成功的活动列表。详情按分圈、FIT 私有缓存和摘要逐级降级，warning 与数据质量一起返回；绝不伪造分圈或时序。真实 FIT 目前可以由手工导出补齐，自动 URL 仍明确标为未完成。

## 12. 如果再给两周，你会做什么？

M9-D 聊天待确认 Memory Candidate 已经完成；下一步做 M9-E 版本化 Memory Eval Suite，量化提取、拒绝、冲突、过期、来源完整性和职责召回。随后补 M6-A3b 真实 DeepSeek 多轮聊天同题验收。不会先增加营养或伤病 Agent；新增职责必须由用户闭环缺口和评测证据驱动。

## 13. 这个项目当前最大的不足是什么？

真实个人数据量仍少；多 Agent 路由没有真实 LLM 同题结果；恢复规则是保守工程阈值而非医学模型；没有部署、并发和真实用户验证。项目强项是边界和可验证性，不是业务规模。

## 14. 如何现场证明不是只有文档？

先运行 `demo-seed --reset` 创建隔离状态，网页现场运行 Coach，展示三个职责节点、Trace 和待确认草案；然后批准一次计划调整，说明服务端重放和 revision。最后打开评测与测试证据，明确合成基线和真实模型结果的区别。
