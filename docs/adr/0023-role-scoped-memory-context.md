# ADR-0023：按职责裁剪记忆上下文，并分离运行 Hash 与审计 Hash

## 状态

接受

## 背景

M9-A、M9-B 已经分别建立长期偏好和版本化周训练记忆，但“数据库里有记忆”不等于“每个 Agent 都应该看到全部记忆”。如果 Execution、Recovery、Plan 直接共享同一份完整对象，会产生三个问题：无关私人字段扩大暴露面；上下文随历史增长而无限膨胀；系统只能说明用了什么，不能说明为什么没有使用其余记忆。

M9-B 的 Planning 路径已经消费周记忆，但 CLI 计划入口没有传入周记忆 Repository，也缺少统一的选中、排除和预算审计，说明仅靠各 Service 自行查询会逐渐产生入口差异。

## 决策

1. 新增统一 `AgentMemoryContext` 与确定性 Memory Context Builder，输入为职责、目标、知识截止时间和可选目标训练周。
2. v1 职责权限和固定预算为：
   - Execution：0 条、0 字符；不读取长期偏好或周记忆；
   - Recovery：最多 2 条、1400 字符；只读取最近有效完整周摘要；
   - Plan：最多 5 条、1800 字符；读取已确认有效偏好和目标周之前的有效周摘要。
3. Plan 周摘要不包含疲劳、酸痛、准备度、疼痛严重度或急性症状；这些恢复字段只允许 Recovery 投影读取。
4. 每个候选都记录选中顺序或排除原因，包括职责无权限、错误目标、未来、过期、被替代、归档、失效、目标窗口之外、条数预算和字符预算。
5. `context_hash` 只包含实际选中投影、职责、时点和预算策略；无关失效记录的增加不应让业务结果变成 stale。
6. `audit_hash` 额外包含全部选中/排除决定和预算统计，用于证明检索过程没有静默丢弃候选。
7. Training Execution、Recovery Assessment 和 Weekly Plan Draft 的结构化输出携带职责 Context；其 Hash 纳入对应业务 `input_hash`。网页周视图和 `runcrew memory context` 提供只读审计入口。
8. 当前继续使用 SQLite 结构化检索，不引入向量数据库、语义相似度或 LLM 自主召回。

## 原因

- 最小字段和角色白名单比“请模型不要看无关信息”的 Prompt 更可验证；
- 固定条数与字符预算让上下文成本可预测并可回归；
- 分开 Context Hash 与 Audit Hash，兼顾业务稳定性和完整检索审计；
- Planning、CLI、网页和 Coach 节点复用同一 Builder，避免入口之间的记忆行为漂移。

## 后果

- 用户和面试官可以看到三种职责分别选中了几条记忆、排除了什么以及预算使用量；
- Execution 的零记忆是显式权限决定，不是暂时没有查到数据；
- Recovery 的周记忆只提供背景，不改变急性红旗和风险阈值；
- Plan 能使用训练量与完成情况，但不会收到不必要的恢复/疼痛细节；
- 预算是 `memory-context-policy/1.0` 的工程选择，后续改变需要版本升级与评测；
- 当前没有保存每次独立 CLI Context 的数据库审计表；Coach Run 会通过嵌套业务结果持久化 Context，其他入口以返回结果和业务 Hash 回放。

## 替代方案

### 所有 Agent 共享完整 Memory 对象

实现简单，但违反最小权限，且上下文成本和私人字段暴露不可控。

### 只记录选中记忆，不记录排除

无法判断记忆是因为失效、未来、无权限还是预算不足而消失，难以排查召回错误。

### 把全部候选和排除决定都放入业务 Hash

审计完整，但新增一条无关归档记录也会让计划或恢复结果失效，因此改用独立 `audit_hash`。

### 使用向量检索和 Top-K

当前记忆只有明确的类型、目标、时点、状态和周区间，结构化过滤已经足够；没有评测证据支持引入语义召回的不确定性。
