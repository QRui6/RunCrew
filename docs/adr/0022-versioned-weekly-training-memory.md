# ADR-0022：版本化周训练记忆只由已确认事实确定性生成

## 状态

接受

## 背景

M9-A 已能保存用户显式确认的长期偏好，但 Planning Agent 仍主要从逐条 Activity 重新计算历史基线。这样可以回放，却无法直接回答“前几周计划完成得怎样、恢复反馈如何、下一周规划究竟使用了哪一版训练历史”。

如果让 LLM 从聊天或原始活动自由生成周总结，会出现三个问题：未确认的活动匹配可能被当成完成事实；相同输入不能稳定回放；记忆被修改或撤销后，已经生成的计划无法判断是否过期。

## 决策

1. 只允许在完整训练周结束后，为非草稿正式计划生成 Weekly Training Memory。
2. 正式记忆只消费知识截止时间之前的以下结构化事实：
   - 正式周计划及其 revision；
   - 状态为 `applied` 的训练执行确认；
   - 被执行确认引用、且不晚于截止时间的规范化 Activity；
   - 训练周内已经提交的 Check-in；
   - 已批准且已经决定的计划变更。
3. 只有用户确认匹配的 Activity 才计入已完成训练量；候选匹配、未确认 Activity 和未来数据都不计入。
4. 记忆保存 `input_hash`、规则版本、来源引用、缺失数据、版本号和 `supersedes_id`，生命周期为 `active / superseded / invalidated`。
5. 知识截止时间只用于筛选可见事实，不直接进入 Hash；因此稍后用相同事实刷新仍返回 `unchanged`。输入事实变化时生成新版本并替代旧版本；人工失效后，同样事实再次生成也必须产生更高版本，不能复活历史记录。
6. Planning Agent 优先使用目标周之前最近的有效周训练记忆，并把记忆 ID、版本和输入 Hash 写入 evidence 与计划输入 Hash；不足时回退到规范化 Activity。
7. LLM 只能解释记忆，不能直接写入、修改或失效正式周训练记忆；当前不引入向量数据库。

## 原因

- 把“模型认为完成了”与“用户确认完成了”严格分开；
- 同一截止时间和同一事实得到可重复结果，便于测试与故障回放；
- 计划能够指出自己依赖的历史版本，记忆变化会自然触发 stale 校验；
- 结构化查询已经能满足当前按目标和周检索的需求，暂时没有引入向量检索的证据。

## 后果

- 用户可以结算上一训练周，在网页、API 和 CLI 查看版本化摘要；
- Planning Agent 的周时长基线更接近“已经确认的训练执行”，而非仅依据设备记录；
- 未完成周、未来计划、未确认活动或已经失效的记忆不会污染后续规划；
- 如果执行确认在周结算后补录，需要主动刷新并生成新版本；当前没有后台自动刷新任务；
- 周记忆是训练事实摘要，不是医学判断、训练效果保证或自然语言日记。

## 替代方案

### 每次规划时重新扫描全部活动与反馈

实现简单，但无法形成明确的跨周版本、来源链和撤销语义，也增加 Context Builder 的负担。

### 让 LLM 直接生成并保存周总结

表达自然，但事实边界和重复运行结果不稳定，无法作为正式规划输入。

### 立即使用向量数据库检索历史

适合大规模非结构化材料，但当前记忆类型、目标、周区间和状态都是明确字段；先使用 SQLite 结构化检索更容易解释和评测。
