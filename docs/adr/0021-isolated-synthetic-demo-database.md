# ADR-0021：求职演示使用隔离且可重置的合成数据库

- 状态：接受
- 日期：2026-08-19

## 背景

RunCrew 已经能够读取真实 COROS/FIT 数据，也会持久化训练计划、主观反馈、长期偏好、对话和 Agent 审核结果。如果直接拿个人数据库做求职演示，会同时带来三个问题：隐私数据可能出现在录屏或仓库中；每次演示后的状态不同，流程无法稳定复现；预先保存 Agent 结论又会让现场演示失去可信度。

## 决策

新增独立的 `demo-seed` 能力，并遵守以下边界：

1. 只允许 CLI 把演示数据库创建在 `data/private/demo/` 下；
2. 数据库已存在时默认拒绝覆盖，只有显式传入 `--reset` 才重置；
3. 活动、目标、计划、执行确认、Check-in 和长期偏好全部由本地代码生成，不读取个人数据库、COROS、FIT、DeepSeek Key 或网络服务；
4. 业务 ID 使用 UUIDv5，给定同一锚点时间时可以稳定复现；
5. 不预先保存对话、Coach 运行和 Agent 结论，关键编排必须在演示现场真实执行；
6. 计划中的“已完成训练”和“待执行训练”根据启动日动态排布，避免周末演示时没有后续任务；
7. 重置前释放 SQLite Engine，兼容 Windows 对数据库文件句柄的锁定行为。

## 原因

- 将演示证据与个人数据彻底隔离；
- 保证现场失败后可以在几十秒内恢复到同一起点；
- 让面试官看到的 Agent Trace、恢复判断和计划草案确实由当前代码生成；
- 把“这是合成业务场景”与“系统确实执行了这些工程链路”明确区分。

## 后果

- 演示包可以公开进入仓库，演示数据库本身继续被 Git 忽略；
- 合成数据只能证明工程链路可运行，不能证明真实用户训练效果；
- 默认锚点随本地日期变化，因此自然语言中的具体日期会变化，但训练闭环结构保持一致；
- 新增 Demo Seed Schema 和专项集成测试，后续字段变化必须同步更新契约。

## 替代方案

### 直接复制个人数据库

拒绝。存在隐私泄漏和演示状态漂移风险。

### 提交一个固定 SQLite 文件

拒绝。二进制数据库不利于审查和维护，也容易悄悄携带历史对话或个人标识。

### 预先保存完整 Agent 回答

拒绝。页面会更稳定，但无法证明 Harness、Skill、Memory 和审核链路在现场真实运行。
