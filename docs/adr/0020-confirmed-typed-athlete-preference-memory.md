# ADR-0020：长期训练偏好使用类型化、显式确认和可追溯写入

状态：接受  
日期：2026-08-19

## 背景

RunCrew 已经持久化对话、Evidence Snapshot、训练目标、计划、执行确认、身体反馈和 Coach Run，但这些状态不能回答“用户长期偏好把长距离训练放在哪一天”。如果直接把聊天文本写入通用 Memory 或向量库，会产生误记、冲突、过期信息继续生效和来源不可追踪等问题。

## 决策

1. M9-A v1 只支持 `preferred_long_run_weekday`，不建立任意 key/value Memory；
2. 写入必须通过 `AthletePreferenceSubmission.confirmed=true`，普通聊天和 Agent 无权自动保存；
3. SQLite `athlete_preferences` 是事实来源，每条记录保存类型、值、来源、确认时间、有效期、Schema 版本和替代链；
4. 同一 key 的相同提交保持幂等，新值把旧版本标记为 `superseded`；停用标记为 `archived`，不做不可审计的硬删除；
5. 到期偏好不会被计划检索，并在产品输出中显示为 `expired`；
6. 当前训练目标的 `available_weekdays` 优先于长期偏好。只有偏好日期也属于目标可训练日且至少安排两节课时，才把长距离课放到偏好日；
7. 周计划 `input_hash` 包含实际读取的偏好版本，Planning evidence 记录偏好 ID、来源、版本和是否采用。偏好改变后，旧草案不能通过激活前重放；
8. 当前使用结构化 SQLite 查询，不引入向量数据库或 LLM 记忆抽取。

## 原因

- 当前只有少量、类型明确的个人设置，SQL 比语义检索更可预测；
- 类型化契约能在写入前阻止未知偏好和非法值；
- 显式确认延续项目“Agent 只建议，用户决定事实写入”的边界；
- 把偏好加入 Hash 和 evidence 后，个性化不会破坏可回放性；
- 先完成一个能被真实业务消费的垂直切片，比保存暂时不会使用的“回答风格”或“训练时间”更诚实。

## 后果

正面：

- 用户偏好可跨重启生效，并能在页面查看、替换和停用；
- Planning Agent 能真正使用长期偏好，同时保留目标级设置优先权；
- 每次计划使用了哪条记忆都可以审计；
- 旧草案会因记忆变化而失效，避免基于过期上下文写入。

限制：

- v1 只有长跑星期一种偏好；
- 普通聊天不会自动生成 Memory Candidate；
- 尚未实现周训练记忆、跨周期检索和独立 Memory Evaluation Suite；
- 当前是单用户本地系统，没有人为加入尚不存在的账户 `user_id`。

## 替代方案

- 通用 `user_memories(key, value)`：扩展快，但类型和消费边界不清晰，拒绝；
- 聊天后由 LLM 自动写入：会扩大误记和隐私风险，推迟到有候选确认与评测之后；
- 立即使用 Chroma/pgvector：当前数据量和查询类型不需要，拒绝；
- 直接修改 `TrainingGoal.available_weekdays`：会混淆目标级约束与跨目标默认偏好，拒绝。
