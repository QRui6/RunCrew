# ADR-0013：激活后的训练计划只能通过用户确认的提案变更

## 状态

接受。

## 背景

RunCrew 将从单次训练复盘扩展为“目标—计划—执行—反馈—调整”闭环。计划 Agent、恢复风险 Agent 和总教练协调 Agent 未来都可能建议修改课表。如果任一 Agent 可以直接写入正式计划，就无法区分建议与用户决定，也难以处理并发建议、旧上下文覆盖和错误恢复。

## 决策

- 草稿计划允许通过确定性 Service 添加训练课；
- 计划激活后禁止直接修改；
- Agent 只能提交 `PlanChangeProposal`，其中必须包含计划 ID、基础版本、提出者、理由和结构化修改；
- 提案不会自动生效，必须产生 `UserConfirmation`；
- 批准时检查 `base_revision`，版本不一致的提案标记为 `stale`，不得覆盖新计划；
- 成功批准后，计划修订号递增，并保留提案和确认记录；
- 训练课改为休息时必须显式清除距离、时长和强度等不再适用的字段。

## 原因

这使不同 Agent 拥有“建议权”但没有不受控的“执行权”，把人类确认落实为领域状态，而不是只写在 Prompt 中。版本检查也使多个专业 Agent 对同一计划提出建议时可以安全失败和重新规划。

## 后果

- 多 Agent 编排必须通过统一 Service 操作计划，不能直接写数据库；
- UI 需要提供待确认提案和批准/拒绝入口；
- 后续 Harness 可以对白名单、确认门、版本冲突和越权写入进行评测；
- 当前仅实现单用户本地状态，不包含账户、团队权限和通用工作流引擎。

## 替代方案

1. **Agent 直接修改计划**：实现简单，但无法审计和阻止错误写入，拒绝。
2. **只在聊天中询问“是否同意”**：没有持久化状态，重启后无法恢复，拒绝。
3. **引入通用事件溯源框架**：现阶段复杂度过高，先用修订号、提案和确认表满足实际需求。
