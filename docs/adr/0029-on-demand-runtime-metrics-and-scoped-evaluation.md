# ADR-0029：从 Runtime 事实按需聚合指标，并隔离合成治理评测

## 状态

已接受，2026-08-20。

## 背景

M10-B 已把 Review 与 Coach 的单次 Trace 持久化为统一 Run/Span。M10-C 需要回答两个不同问题：

1. 产品路径最近真实发生了什么，例如成功率、拒绝率、重试率和延迟；
2. 治理防线在故障注入下是否按版本化期望工作。

如果把二者混在同一张指标表，离线合成故障会污染产品运行数据；如果预先写入汇总值，又会引入指标漂移、重复回填和新的数据生命周期。

## 决策

- 不新增汇总指标表；在读取时从仍处于30天保留期内的正式 Run/Span 确定性重算；
- 指标窗口限制为1—30天，最多聚合500条 Run，超限显式返回 `truncated=true`；
- P50/P95 使用 nearest-rank，空样本返回 `null`；所有比例同时返回分子、分母和值；
- 按 workflow、workflow version、tool、role 和 termination reason 分组，其中 role 只由 workflow/node 派生；
- 产品 Runtime 指标不写入离线 Evaluation；观测写入失败由于没有事实行，不能进入产品聚合，API 必须返回覆盖说明；
- 单独建立 `runtime-governance-eval/1.0` 合成套件，验证未注册工具、参数篡改、确认绕过、非法输出和 best-effort 观测失败隔离；
- 工程观测页面及其三个 Runtime API 全部只读，不提供删除、重放、审批或业务写入。

## 结果

优点：

- 指标可以从事实重算，不存在汇总表与 Run/Span 不一致；
- 合成故障不会污染产品成功率和延迟；
- 空样本、截断与写入缺口均可见，避免过度声明；
- 页面、API、Schema 和求职证据使用同一口径。

代价：

- 当前聚合适合本地、30天、最多500 Run 的规模，不是大规模 OLAP；
- best-effort 写入失败无法由 Runtime 表自身计数，只能通过故障评测验证隔离语义；
- 当前 P95 是本地流程耗时，不代表生产网络或模型服务延迟。

## 不采用的方案

- 不新增 Metrics Agent：指标是确定性统计，不需要模型推断；
- 不把离线评测写入 Runtime 表：否则产品指标会被测试流量污染；
- 不接入 Prometheus、OpenTelemetry Collector 或分布式 Trace 后端：当前本地规模和证据不足；
- 不把缺失写入记录估算成0或100%：无法验证的数据保持未知。
