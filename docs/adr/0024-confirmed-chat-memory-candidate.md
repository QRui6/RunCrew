# ADR-0024：聊天只能提出可过期的类型化 Memory Candidate

## 状态

接受

## 背景

M9-A 至 M9-C 已完成正式长期偏好、周训练记忆和按职责 Context，但用户仍需进入训练抽屉手工重复填写已经在对话中表达过的偏好。如果聊天 Policy 或 LLM 直接调用正式 Memory 写入，一句临时安排、否定表达或模型误解就会跨会话影响后续计划。

## 决策

1. 普通用户消息只能产生独立 `MemoryCandidate`，候选不是正式 `AthletePreference`，也不会进入 Agent Memory Context。
2. v1 只提取现有业务能够消费的 `preferred_long_run_weekday`，使用高精度确定性规则识别长期、单一星期、非否定的长跑偏好；临时安排、多星期歧义、问题和不支持的记忆类型不生成候选。
3. 候选保存原消息 ID、原文 SHA-256、类型化值、置信边界、规则版本、Candidate Hash、七天有效期和生命周期，不复制保存原始消息正文。
4. 同 key 新候选会把仍待确认的旧候选标为 `superseded`；候选状态为 `pending / confirmed / rejected / superseded / expired`，历史不硬删除。
5. 浏览器确认接口只接受 `decision + expected_candidate_hash`，不接受 key、value、来源或正式偏好字段。
6. 确认时服务端重新计算 Candidate Hash，并重新读取原始用户消息核对 conversation、role 与文本 Hash；任一变化都拒绝写入。
7. 校验通过后，服务端从候选重建 `AthletePreferenceSubmission(confirmed=true)`，复用 M9-A 的幂等、替代和来源写入服务；拒绝、替代、过期候选永不写入正式 Memory。
8. 候选提取与离线/DeepSeek 回答 Policy 解耦。LLM 不拥有候选或正式记忆写工具；即使回答失败，已经保存的用户消息和候选仍可在重新加载对话后审核。

## 原因

- 把“系统识别到可能值得记住”与“用户确认这是长期事实”分成两个状态；
- 复用正式偏好服务，避免聊天入口形成第二套写入语义；
- 原消息 Hash、Candidate Hash 和服务端重放共同防止前端或本地记录漂移；
- 当前只有一种受支持记忆，高精度规则比引入模型抽取、任意 key/value 或向量库更容易评测和解释；
- 七天有效期避免长期悬而未决的建议在用户忘记上下文后被误确认。

## 后果

- 用户可以在自然对话里表达长期长跑日，直接在原消息下确认或忽略；
- 未确认候选不会影响 Planning、Recovery 或 Execution；
- 候选确认后会留下从正式偏好回到 Candidate 和原消息 ID 的来源链；
- v1 会保守漏掉复杂、隐含或跨消息表达，这比误写正式记忆更可接受；
- 当前没有使用真实 LLM 提取，也没有独立 Memory Evaluation Suite；下一阶段用版本化场景衡量提取、拒绝、冲突、过期和来源完整性。

## 替代方案

### 让聊天 LLM 直接调用偏好写入工具

交互步骤少，但把概率性理解直接变成跨会话事实，违反现有人工确认边界，拒绝。

### 让 LLM 生成任意文本候选

表面灵活，但候选无法被现有业务确定性消费，类型、冲突和失效策略不清晰，拒绝。

### 把消息全文复制进候选表

展示方便，但扩大私人文本副本和保留范围；候选只保存消息引用与 Hash，页面从原会话显示原文。
