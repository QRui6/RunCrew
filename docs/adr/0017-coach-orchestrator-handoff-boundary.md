# ADR-0017：Coach Orchestrator 的最小交接与确认中断边界

状态：接受
日期：2026-08-13

## 背景

Recovery、Plan 和 Execution 三个确定性 Skill 已经存在，但简单地在一个 Prompt 中同时暴露全部工具，会让模型同时拥有判断、路由和修改计划的能力，也难以证明每个职责只看到了必要上下文。跨节点结果如果只靠自然语言转述，还会丢失上游证据和目标范围。

## 决策

1. Coach Policy 只选择委派节点或结束，不直接调用数据库、解释原始活动或批准计划；
2. Execution、Recovery、Plan 节点分别只绑定一个类型化工具；
3. Harness 根据用户运行请求生成 Execution/Recovery 请求，根据已校验 Recovery 输出生成 Plan 请求，Policy 不能篡改参数；
4. 交接 Trace 只保存字段名和请求 SHA-256，不保存身体反馈、活动详情或完整工具参数；
5. 节点输出必须通过 Pydantic，并属于同一个 `goal_id`、`plan_id` 和恢复 `input_hash`；
6. Plan 节点只有 `prepare_change` 权限，不能持久化或批准；产生调整草案后工作流终止为 `awaiting_user_confirmation`；
7. 缺少新鲜反馈或出现运动安全红旗时安全阻断，不为了完成流程继续调用 Plan 节点；
8. 确定性 Policy 作为可回放基线，未来 LLM 只能替换动作选择层，不能绕过 Harness。

## 原因

- 多 Agent 的价值来自职责、上下文和权限隔离，而不是角色名称数量；
- 类型化交接可以验证上游事实没有在自然语言中被改写；
- 用户确认中断点把“建议权”和“生效权”分开；
- 确定性基线便于随后做同题 LLM 编排评测。

## 后果

- v1 路由次序是确定性的，尚不能声称 LLM 已稳定完成多工具规划；
- CLI 只返回变更草案；用户若同意，仍需通过训练闭环的提案与确认命令应用；
- 需要在 M7-E 为跨节点冲突、重试、越权和事实一致性建立版本化评测套件。

## 替代方案

- 单个大 Agent 直接拥有三个工具：实现短，但职责、上下文和写权限不可审计；
- 让节点自由传自然语言：灵活，但无法校验目标范围和证据血缘；
- Plan 节点直接写数据库：交互更短，但违背用户确认和 revision 防并发边界。
