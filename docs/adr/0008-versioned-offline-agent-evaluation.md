# ADR-0008：先建立版本化离线评测基线再接入真实 LLM

- 状态：接受
- 日期：2026-08-09

## 背景

M4 已经完成 Agent Harness 和 Loop，但默认 Policy 是确定性的。如果直接接入真实 LLM，只观察几次成功演示，无法区分模型动作错误、Harness 回归、工具故障或业务事实被修改，也无法回答“多 Agent 是否真的更好”。

## 决策

M5-A 先建立不含私人数据的版本化 JSON 评测套件，固定覆盖正常任务、缺数降级、瞬时恢复、超时、非法输出、越权、参数篡改、确认门、提前结束和预算耗尽。

评测报告使用 Pydantic 和 JSON Schema，固定统计：

- 全部预期通过率；
- 正常任务完成率；
- 护栏通过率；
- Schema 通过率；
- 事实一致率；
- 被拒绝后底层工具错误执行数；
- 平均逻辑工具调用和工具尝试；
- P95 延迟与退出原因分布。

评测套件使用稳定 `suite_hash` 标识；报告默认只允许写入 `data/private/`。真实 LLM Policy 必须复用 M4 Action Schema，并与当前离线基线对照后才能讨论多 Agent。

## 原因

- 先建立可重复的 ground truth，再衡量模型变化；
- 将“正常任务完成”和“故障时安全退出”分开统计；
- 使用故障注入稳定覆盖真实环境难以重复的异常；
- 护栏用例验证工具没有在拒绝后偷偷执行；
- 评测用例不含真实跑步数据，可以安全进入私有仓库并持续回归。

## 后果

- 当前报告只能证明 Harness、确定性 Policy 和脚本化故障场景满足基线，不能代表真实模型质量；
- 延迟数据受本机环境影响，只作为基线观察，不作为当前硬门槛；
- 接入 LLM 后需要增加模型 ID、Token、费用和动作解析失败指标；
- 多 Agent 必须用相同套件对照，不能只凭主观架构偏好拆分。

## 替代方案

- 直接用真实 COROS 历史数据评测：拒绝，因为隐私风险高且数据覆盖不足；
- 只依赖单元测试：拒绝，因为无法形成跨场景聚合指标和可比较报告；
- 接入 LLM 后再补评测：拒绝，因为没有改造前基线；
- 先实现多 Agent 再比较：拒绝，因为会同时改变模型、上下文和编排变量。
