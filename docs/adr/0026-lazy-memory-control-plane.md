# ADR-0026：Memory 控制面按需聚合并复用既有写入状态机

## 状态

接受

## 背景

M9-A 至 M9-E 已形成候选、正式偏好、周训练记忆、职责 Context 和版本化评测，但用户需要在聊天消息、训练闭环与 CLI 之间切换，才能回答“系统记住了什么、来自哪里、是否仍生效、哪个 Agent 能读取、如何撤销”。如果为控制面另建一套写入逻辑，会让确认、完整性重放和生命周期产生第二个事实来源。

## 决策

1. 新增 `MemoryControlService`，只负责按需聚合 Candidate、Athlete Preference、Weekly Training Memory 和三个职责的正式 Context 审计，不拥有新的记忆写权限。
2. `/api/memory/overview` 仅在用户打开“记忆档案”时读取，普通聊天首屏不承担跨目标聚合与 Context Builder 成本。
3. Candidate 来源正文不复制到新表；控制面通过 `source_message_id` 读取原消息并只返回最多240字符的折叠摘要。Provider 外部 ID、原始载荷、坐标和 Token 不进入 DTO。
4. 候选确认/拒绝复用 `ChatService` 的 Candidate Hash 与原消息完整性重放；偏好停用和周记忆失效复用 `TrainingOperationsService`。控制面只增加统一路径别名，不创建第二套状态机。
5. 停用与失效保留原记录，不提供硬删除；后续 Context Builder 根据生命周期自动排除并留下原因。
6. 周记忆失效请求增加 `confirmed: true` 契约；浏览器必须二次确认。职责可见性同时展示条数/字符预算、选中结果和逐条排除原因。

## 原因

- 用户能集中审计和撤销记忆，同时服务层仍只有一个正式写入边界；
- 按需加载避免把管理型元数据和跨目标查询加入每次聊天；
- 保留历史版本比硬删除更适合解释计划依据和面试演示；
- 直接展示 Context Builder 的真实决策，不另写一套只用于界面的“可见性解释”。

## 后果

- M9 的用户闭环完成：候选可确认/拒绝，正式偏好可停用，周记忆可失效，职责使用原因可查看；
- 控制面响应是当前时点的投影，到期 Candidate 会在读取时正式过期，偏好有效性按当前时点展示；
- 当前没有新记忆类型、向量数据库、LLM 写入权限或硬删除能力；
- 若未来增加删除或导出，必须单独定义审计、确认和数据恢复策略。

## 替代方案

### 在训练闭环抽屉继续增加零散按钮

实现成本低，但无法集中回答来源、生命周期和职责可见性，拒绝。

### 为控制面新建 CRUD Service

会复制 Candidate、Preference 和 Weekly Memory 的写入规则，增加状态漂移风险，拒绝。

### 页面加载时预取全部记忆

会让普通聊天承担非必要查询和 Context 构建成本，拒绝；改为打开抽屉时按需加载。
