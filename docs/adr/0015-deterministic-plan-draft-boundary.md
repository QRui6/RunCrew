# ADR-0015：确定性计划草案与提案边界

状态：接受  
日期：2026-08-13

## 背景

Recovery Skill 已能输出 `plan_action`，但若让 LLM 直接计算周跑量、修改激活计划或批准自己的建议，就无法稳定回放，也破坏 M7-A 的用户确认边界。

## 决策

1. Plan Skill 使用确定性 Service 生成周计划草案或 `PlanChangeProposal` 参数；
2. 周计划只使用用户目标、可训练星期和截止时点之前的规范化活动；
3. 历史不足时使用明确标注的保守模板，不根据目标成绩编造高强度处方；
4. Recovery 的 `plan_action` 是跨职责契约，Plan Skill 不重新判断风险；
5. 结果只停留在草案层，不保存、不批准，也不覆盖已有计划；
6. 变更提案绑定 `plan_id + base_revision`，最终仍由用户确认。

## 原因

- 计算规则可测试、可版本化、可用同一输入 Hash 回放；
- Recovery 与 Plan 职责分离，跨 Agent 只传递结构化最小上下文；
- LLM 可负责解释和协调，但不能绕过确定性事实与写入护栏；
- 缺数据、比赛周和风险升级场景可以安全失败。

## 后果

- M7-B2 的“计划 Agent”能力当前是 Skill/Service，不等于已完成自主 Plan Agent；
- v1 计划较保守，未处理天气、海拔、力量训练和比赛策略；
- 后续 Harness 可以把 Recovery 与 Plan 封装成两个职责节点，而不用重写业务规则。

## 替代方案

- 让 LLM 输出完整课表：自由度高，但数值不可回放且更易越权；
- Recovery Skill 直接修改计划：实现简单，但职责冲突且无法保留用户最终控制；
- 先搭角色 Prompt 再补工具：演示快，但不能证明多 Agent 协作的真实业务价值。
