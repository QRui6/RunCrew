# ADR-0018：Coach 草案批准前服务端重放

状态：接受
日期：2026-08-13

## 背景

M7-D 允许用户在聊天产品中审核 Coach 生成的计划调整。浏览器页面可能被篡改，Coach 运行后身体反馈、活动或计划 revision 也可能发生变化。如果批准接口直接接受前端传回的 patch，用户确认的就不一定是当时由受控节点生成的建议。

## 决策

1. Coach 运行请求、完整受校验结果和计划输出哈希保存到本地 `coach_runs`；
2. 浏览器审核请求只允许 `decision + comment`，禁止提交 changes、reason 或 revision；
3. 拒绝只关闭该运行记录，不创建正式提案；
4. 批准前服务端使用原请求重新执行同一 Coach 工作流；
5. 只有 fresh result 仍需确认、`planning.input_hash` 相同且完整草案相同时，才由服务端创建正式提案并立即执行用户批准；
6. 任何差异都把运行标记为 `stale`，不修改计划；
7. 最终应用继续由 M7-A `TrainingCycleService` 的 plan revision 保护。

## 原因

- 浏览器不成为计划 patch 的可信来源；
- 用户批准时使用最新活动、身体反馈和计划状态；
- 保留 Coach 建议、用户决定和正式计划变更之间的审计链；
- 双层防护：工作流重放验证业务输入，revision 防止并发覆盖。

## 后果

- 批准操作会额外运行一次本地确定性 Coach；
- 如果数据更新，用户需要重新查看新建议；
- v1 只支持本地确定性 Policy，不在批准动作中调用付费模型。

## 替代方案

- 前端回传 patch：实现简单但可以被篡改；
- 保存时立即创建 pending proposal：可恢复性好，但用户拒绝也会留下不必要的正式提案；
- 只校验 plan revision：无法发现身体反馈或活动变化导致的建议漂移。
