# ADR-0011：连续对话使用固定证据快照与有界历史

- 状态：接受
- 日期：2026-08-09

## 背景

M6-A1 的 Dashboard 能展示 Activity、evidence、Trace 和评测，但不能满足用户围绕自己的跑步数据连续追问。直接把数据库、全部历史或 Provider 原始数据交给 LLM，会破坏已有事实边界，也会让上下文随轮次无限增长。

## 决策

- 一个 Conversation 固定绑定一个 RunCrew 内部 Activity ID；
- 首次提问运行现有 Review Agent，并把通过 Schema 校验的 `TrainingReviewResult` 与脱敏 Trace 保存为证据快照；
- 同一 Conversation 的后续追问复用该快照，不重复读取 Provider 原始载荷或重新计算事实；
- 模型上下文最多包含最近8条消息，单条最多1200字符；
- LLM 只负责生成结构化 `ChatAnswer`，evidence 引用必须来自快照中的 finding 类型；
- 默认使用离线回答；DeepSeek 必须由用户显式开启，且只接收脱敏上下文；
- 对话和消息持久化在本地 SQLite，工程观测台继续作为独立入口保留。

## 原因

- 固定快照让一次对话中的事实口径稳定并可回放；
- 有界历史控制 Token、延迟、费用和提示注入影响面；
- 复用 Review Harness 避免为 Web 聊天复制一套旁路业务规则；
- 本地持久化让聊天真正可连续使用，而不是刷新即丢失的前端演示。

## 后果

- 同一会话暂时不能切换目标活动；需要比较两次跑步时应创建新会话或未来设计显式的比较 Skill；
- 活动数据发生更新后，已有会话仍保持旧快照，保证历史回答可解释；
- 新增两张 SQLite 表，后续需要数据删除、导出和迁移方案；
- 模型回答仍需独立多轮评测，不能只凭 Schema 校验声称内容完全安全。

## 替代方案

- 每轮重新运行 Skill：拒绝，因为会浪费调用且可能让同一对话事实口径漂移；
- 把全部数据库和对话历史交给模型：拒绝，因为隐私、成本和上下文不可控；
- 只使用浏览器 `localStorage`：拒绝，因为会话是产品数据，需要由本地后端作为事实来源；
- 删除原 Dashboard：拒绝，因为它仍然是有价值的工程观测入口。
